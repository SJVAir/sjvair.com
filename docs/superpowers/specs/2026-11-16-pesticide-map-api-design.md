# Pesticide API additions for the dashboard Map

2026-11-16. Server side of data-dashboard Release 1, step 5, spec 5 (pesticide use by
section and township, and spray notices on the dashboard's Map widget).

## Why

The dashboard's Map widget shows pesticide use and spray notices. It shades use by
township when zoomed out and by section from about zoom 11, for a fixed year or one month
of a year, opening on the latest year with data. Spray notices follow the Map's day stepper.
The dashboard stores no generated English and hardcodes no labels, colours or links, so
the server has to provide the shading classes, the text and the lookups that today live
only in the explorer's templates and JavaScript.

## Goals

- Valley-wide quantile class breaks for section and township shading, computed and cached
  on the server.
- `category` and `iarc_group` filters on `sections/`, `townships/` and `notices/active/`,
  with the same names, values and counting as `pesticides/place/`.
- Spray notices active on a given Pacific day.
- Server-owned explainer text, badges, the colour ramp, the years with data and the
  SprayDays link in `pesticides/meta/`.
- A documented, permanent township id.

## Non-goals

- Changing the Pesticides explorer. It keeps its templates, its on-screen ranking and its
  hardcoded copy. Moving it onto the new meta or classes is deferred (with the coordinator).
- Diverging (year-over-year change) classes. Only the sequential classes are served.
- A `sections/?township=` filter. The dashboard loads sections by bbox.
- Aligning `sections/`'s `chemical`/`product` (CDPR codes) with `place/`'s sqids.

## Anti-goals (a failure even if it works)

- **Any change in behaviour of the Pesticides or Facility Emissions explorers.** Every
  addition is a new parameter or a new field. A request without the new parameters gets
  exactly today's response. Shared helpers they use (`maps.py`: `quantile_classes`,
  `RAMP`, `NO_DATA`, the county maps; `stats.by_township`; `apply_filters`) keep their
  behaviour; new code goes beside them. Speed-ups that keep the output identical are fine.
- Pounds, acres or applications that differ from `pesticides/place/` for the same filters.
- English generated by the dashboard or stored in it: text is served from the notes YAML.

## Constraints

- Branch from and PR into `develop` (Release 1). Work in `.worktrees/`.
- No migration is planned. The deploy step for each PR is stated in its description
  ("none", if that holds).
- Measure cold and cached timings locally for the class breaks and put them in PR 2.
- The local stack is shared. Measuring is read-only.

## Approaches (class breaks)

1. **Compute on first request, cache under the pesticide data version (picked).** 16–135 ms
   locally per year/month/filter set (warm DB), 24 numbers per entry, retired by the next
   import. Nothing to schedule, and rare filter sets cost only the people who ask for them.
2. Precompute the unfiltered year and month combinations in the post-import warm-up
   (`warm.py`). This saves the first viewer about 0.1 s but adds import work and can't
   cover filters. It can be added later if cold loads in production prove slow.
3. Store the breaks in a table. Durable, but it needs a migration and rebuild code for very
   little data.

The user picked (1).

## PR 1: notices

### `notices/active/?date=YYYY-MM-DD`

- `date` is a Pacific calendar date. Notices **active on day D** are those whose application
  window covers D:
  `start(D-4) <= scheduled_application < start(D+1)`, where `start(X)` is 00:00
  America/Los_Angeles on date X, built with `make_aware` on calendar dates (never
  `timedelta(days=…)` across a DST change). This is the 4-day rule `scheduled_end` already
  uses (an application may begin up to `NOTICE_GRACE_DAYS` after its scheduled time).
- Works for any date, past or future. A past day can include notices that
  `notices/archive/` lists; that is intended.
- Order (`scheduled_application`, `pk`), the 2,000 cap and every existing filter apply
  unchanged. Without `date=`, the queryset is today's `_upcoming` one.
- Invalid date (not `YYYY-MM-DD`, or out of range): 400 `{"error": "date must be YYYY-MM-DD"}`,
  the endpoint's existing error shape.
- With `date=`, every feature's `properties` also has **`past`**: `true` when its window
  has ended as of now (`scheduled_application < now - NOTICE_GRACE_DAYS`, the archive's
  rule), else `false`. Without `date=` the property is absent, as today.

### `category` and `iarc_group` on `notices/active/`

- `category`: repeated or comma-separated `Chemical.Category` values, any of them (OR),
  validated with `place/`'s `CategoryListField`. `iarc_group`: one `Chemical.IARCGroup`
  value (`PlaceChoiceField`'s choices).
- A notice matches when any of its chemicals matches
  (`chemicals__categories__overlap`, `chemicals__iarc_group`), kept unique by the existing
  `.distinct()`.
- An unknown value is a 400 in the endpoint's shape: `{"error": "<the field's message>"}`
  (e.g. `Unknown category: foo.`). *(Builder's call: this endpoint's shape, not `place/`'s
  `{"errors": {...}}`.)*
- These also apply to `notices/archive/`, which shares the base class. *(Builder's call:
  it's harmless and keeps the two endpoints alike. They're documented on both.)*

### Settled-day cache

- A request with `date=D` is **settled** when now is on or after the later of `start(D+5)`
  and `start(D+1) + NOTICE_GRACE_DAYS` (96 real hours). Every window that could cover D
  (latest start just before `start(D+1)`) has then ended, so every `past` is `true`. The
  second term matters only in a week with a DST change, where `start(D+5) − start(D+1)` is
  95 h. *(Builder's call, from the review: never cache a settled day showing `past: false`.)*
- **A settled day can still change**, and the cache must follow it. The daily SprayDays
  fetch (`tasks.fetch_pesticide_notices`, 14:00 UTC; `spraydays._upsert_application` runs
  `update_or_create`) rewrites `scheduled_application`, chemicals and products of the
  notices SprayDays still lists. So a rescheduled or edited notice can enter or leave a past
  day. **The user's choice:** the fetch bumps a **notices version**
  (`pesticides:notices-version`, set like `stats.bump_data_version`, no expiry; a missing
  value starts a new one) when it finishes. The version is part of the endpoint's cache key,
  so the first request after a fetch recomputes. A fetch that fails partway still bumps it
  (in a `finally`), since some notices may already have changed.
  *(Builder's call: put the version in the key for every `notices/active/` and
  `notices/archive/` request, not only settled ones. It only makes cached answers fresher,
  and the explorer's output is otherwise unchanged.)*
- Settled responses are cached server-side for 24 h. Everything else keeps
  `NOTICE_CACHE_TTL` (5 min). `CachedEndpointMixin` uses one class-wide `cache_timeout`, so
  the endpoint picks the timeout per request (e.g. by overriding where it is read).
  *(Builder's call, as long as the mixin's behaviour for other views is unchanged.)*
- `past` is computed against now, so a 5-minute cache can show a flag up to 5 minutes late.
  That's accepted. A settled day's `past` values are all `true` and stable.

### The charts' filter values on the map endpoints

Added 2026-11-16 at the dashboard's request: the Map uses "the same filters as charts", and
charts send `place/`'s values. This applies to `sections/`, `townships/`, `notices/active/`
and `notices/archive/`. **The user's choices:** separate parameter names for ids (a), the
method mapping, and the commodity answer below.

- **`chemical_id`, `product_id`, `commodity_id`** take our sqids, validated with `place/`'s
  `SqidChoiceField`. The existing `chemical`/`product`/`commodity` keep taking CDPR codes,
  unchanged (the explorer sends codes, and an all-digit sqid can't be told from a code).
  Giving both forms of one filter is a 400:
  `{"error": "give chemical or chemical_id, not both"}` (likewise for product and commodity).
  An id that isn't one, or names no row, is a 400 with the field's message
  (`Not a chemical id.` / `No chemical has this id.`).
- **`aerial_ground`** takes `place/`'s codes `G`, `A`, `F`, `O`, `none`.
  - On sections and townships it means the same as the existing `method` (rollup codes;
    `none` is blank).
  - On notices it maps to SprayDays' wording: `G` → `Ground`, `A` → `Aircraft`,
    `F` → `Fumigation` (case-insensitive), `O` → any other non-blank method, `none` → blank.
  - An unknown code is a 400. The existing `method` parameter is unchanged on all of them.
    If both `method` and `aerial_ground` are given, both apply.
- **Commodity on notices:** SprayDays notices record no crop. `commodity_id` on a notices
  endpoint is a 400: `{"error": "notices don't record a commodity"}`. Plain `commodity`
  stays ignored there, as today. Meta's `notice_filters` lists the value filters the
  notice endpoints accept: `chemical_id`, `product_id`, `category`, `iarc_group`, `narrow`,
  `aerial_ground`.
- **Same chemical on notices:** `chemical_id` goes in the same single `.filter()` as
  `category`/`iarc_group`, so together they must hold on one chemical, as `place/` filters
  ingredient rows.
- **Counting on sections/townships:** `chemical_id` counts like `chemical` (per-row columns).
  `product_id`/`commodity_id` count like `product`/`commodity`.
- **PR 2:** `classes`' value filters include `chemical_id`, `product_id`, `commodity_id` and
  `aerial_ground`. Category/IARC counting treats `chemical_id` as `chemical`.

### `pesticides/meta/` additions

- **`notes`**: `{key: {key, title, summary, detail, source_url}}` (`detail` may be `null`),
  from `notes.all_notes()`, i.e. `datafiles/pesticide-health-notes.yaml`. It serves every note
  in the file. They're all public explainer copy, and serving all of them means one source
  and no list to keep in sync. *(Builder's call; at minimum `noi_meaning`, `pur_lag`, `badges`,
  `prop65`, `carb_tac`, `iarc_1`, `iarc_2a`, `iarc_2b`, `iarc_3`, `california_restricted`.)*
  `pur_lag` is the data-lag text. It also covers the deferred dashboard note on when
  pesticide data is released.
- **`badges`**: `[{key, label, note}]` in the explorer's order
  (`classification-badges.html`):
  - `prop65` "Prop 65" → note `prop65`
  - `carb_tac` "CARB TAC" → `carb_tac`
  - one per IARC group, `iarc_1` "IARC 1", `iarc_2a` "IARC 2A", `iarc_2b` "IARC 2B",
    `iarc_3` "IARC 3" → the matching note
  - `california_restricted` "Restricted" → `california_restricted`

  `note` is a key into `notes`. No colours or styling are served. Badge keys are permanent.
- **`links`**: `{spraydays_signup: SPRAYDAYS_URL}` from `camp/apps/pesticides/places.py`.
- Existing meta keys are unchanged. Meta stays `public, max-age=86400`.

## PR 2: use

### `category` and `iarc_group` on `sections/` and `townships/`

- Same fields and validation as above. A bad value is a 400 `{"error": …}` like the endpoints'
  other errors.
- Either one moves the request off `PesticideSectionTotal` (add both to
  `SECTION_FILTER_PARAMS`' logic) and onto the rollup, filtered by
  `chemical__categories__overlap` / `chemical__iarc_group`.
- **Counting matches `place/`** (`counting_mode`, `places.monthly_use`): pounds sum
  `lbs_chemical`. With a category or IARC filter and no `chemical`, acres and applications
  take the MAX per record key (`places._RECORD_KEY`) and then sum per section, because the
  filter can keep several ingredient rows of one record, and the once-per-record columns sit
  on a designated row the filter may drop. `lbs_product` under that mode: the MAX per record
  key of `lbs_product`. *(Builder's call.)* With `chemical` as well, the per-row columns are
  used, as today.
- Townships fold the same per-section rows through `township_index()`. A new helper beside
  `stats.by_township`; `by_township` itself is unchanged.
- A test checks that a section's (and a township's) figures under a category filter equal
  `place/`'s for a region covering exactly that section (or township), year and month.

### `classes=1` on `sections/` and `townships/`

- Opt-in: only the value `1` turns it on. Without it the response is byte-identical to
  today's.
- Adds a top-level `classes` to the FeatureCollection:

  ```json
  "classes": {
    "lbs_chemical":  {"breaks": [b0, …, b7], "min": m},
    "acres_treated": {"breaks": […], "min": m},
    "applications":  {"breaks": […], "min": m}
  }
  ```

  `breaks[i]` is the inclusive upper bound of class i (`maps.quantile_classes`: up to 8
  classes cut on distinct positive values, so fewer when there are few distinct values).
  `min` is the smallest positive value, so the legend can label the first class. *(Builder's
  call.)* Zero is no data: it's left out of the classes and drawn with `ramp.no_data`. With no
  positive values: `{"breaks": [], "min": null, "colors": []}`.
- **`colors`** (added 2026-11-16 after #336, at the dashboard's request): each figure also
  carries `colors`, one fill per class in break order (`maps.sample_ramp(RAMP, len(breaks))`,
  the same fills `quantile_classes` gives the explorer's class legend; `[]` with no breaks). No data stays meta's
  `ramp.no_data`. Clients never re-implement the sampling. The cache name became
  `classes-v2` so entries without `colors` are never served.
- **Population:** every section (for `sections/`) or every township (for `townships/`) in
  the valley, meaning every MTRS region the rollup has, for the request's year (or
  `year=all`), month and value filters (`month`, `chemical`, `product`, `commodity`,
  `method`, `narrow`, `category`, `iarc_group`). Spatial scope (`bbox`, `lat`/`lng`/`radius`,
  `region`/`buffer`, `county`) never changes the classes. *(Builder's call: the dashboard
  sends only year, month, category and IARC.)* **Each month is ranked on its own** (the
  user's choice): `month=6` ranks June's values only.
- With `compare=`, `classes` describes the scope year's values (not the change). *(Builder's
  call: the dashboard doesn't compare.)*
- **Cache:** `stats.cached(stats.all_years_key('classes', level, year, month, <md5 of the
  sorted value filters>), …)`, no TTL, retired by the data-version bump on import. The bbox
  never enters the key. The surrounding hourly response cache (`CachedEndpointMixin`) is
  unchanged.
- The figures being ranked are the same ones the features carry, from the same counting
  path, so a feature's value always falls in the classes.
- Unfiltered years read `PesticideSectionTotal` (16 ms + 9 ms locally). Everything else
  groups the rollup over the valley (28–135 ms locally).

### `pesticides/meta/` additions

- **`years`**: years with data, newest first (`stats.available_years()` reversed).
- **`ramp`**: `{colors: maps.RAMP, no_data: maps.NO_DATA}`. Both are read from `maps.py`, not
  copied; that's the explorer's 8-step blues and `#f0f0f0`.
- **`notes.shades_valley`**: a new YAML entry (the explorer's `shades` is unchanged):
  - title: "What the shades mean"
  - summary: "Darker squares had more of what the map shows (pounds, acres treated, or
    applications) in that year or month. Every section or township in the valley is ranked
    together, so a color means the same range anywhere on the map, but not from one month to
    the next. Gray means nothing was reported."
  - source_url: the CDPR PUR page `shades` uses.

  The user approved this wording. It doesn't need to be in `REQUIRED_KEYS`.

### `sections/<id>/` `top_chemicals` badges

- Each `top_chemicals` row gains `badges: [<badge key>, …]`, in meta's `badges` order: `prop65`
  if `is_prop65`, `carb_tac` if `is_tac`, `iarc_<group lowercased>` if `iarc_group`,
  `california_restricted` if `is_california_restricted`. The same tests as
  `classification-badges.html` (without its `hide_iarc` page option). `is_of_concern` stays.
- One helper produces the list from a `Chemical` and lives with the meta badge list, so the
  keys are defined once.
- The section-detail response cache gains a `cache_key_version`, so cached rows without
  `badges` aren't served.

### Township id

- `townships/` `id` (and `name`) is the PLSS township designation, the section name minus
  its `-NN` suffix, e.g. `MDM-T14S-R20E` (`townships.township_of`). Document it as permanent
  on the endpoint docstring and in CLAUDE.md: it changes only if the MTRS sections are
  reimported under different names. No code change.

## What clients react to (server side)

- New optional parameters: `date`, `category` and `iarc_group` on `notices/active/` (and
  archive); `classes`, `category` and `iarc_group` on `sections/` and `townships/`.
- New fields: `properties.past` (with `date=`), `classes`, `top_chemicals[].badges`, and
  meta's `notes`, `badges`, `links`, `years`, `ramp`.
- Nothing existing changes shape.

## Testing

- Every existing pesticide test passes unchanged.
- Explorer guards: for the requests the explorer makes today (without the new params),
  responses equal the pre-change ones; `maps.quantile_classes`/`RAMP` untouched; emissions
  views' tests pass.
- Notices: window boundaries (exactly `start(D-4)` in, just before `start(D+1)` in,
  `start(D+1)` out), DST weeks, `past`, filters (any chemical matches, unknown → 400),
  settled-day timeout chosen per request, the DST-week settle instant, and a notices fetch
  (mocked client) bumping the version so a cached settled day recomputes.
- Use: category/IARC counting equals `place/`; classes over the whole valley regardless of
  bbox; a month ranked alone; the cache key ignores spatial params; an import (version bump)
  retires classes; zero excluded.
- Meta: notes from the YAML, badge keys resolve to notes, links, years, ramp.
- Timings for PR 2: cold and cached, for a year, a month, and each with a category, at
  section and township level.
